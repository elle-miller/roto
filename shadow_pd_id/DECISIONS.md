- **2026-07-08** — Optimizer exposes only **3 free parameters per joint: `Kp`, `Kd`, `Fc` (Coulomb/dynamic friction)** — NOT 4. Viscous friction (`Fv`) is fixed at 0 and folded into `Kd`, because on a position-commanded joint both produce torque `= -coefficient * velocity` — mathematically identical effects, so only their *sum* is identifiable from motion data no matter how good the optimizer is. Fitting both as independently-free parameters would let the optimizer trade one for the other arbitrarily (an underdetermined fit dressed up as 2 numbers). Only Coulomb friction (`sign(velocity) * Fc`, a genuine nonlinearity) is separately observable. If a real physical reason to split `Kd`/`Fv` ever comes up, the sim-side API already supports it (`joint_viscous_friction_coeff`); the code just doesn't expose it as a free parameter by default.
- **2026-07-08** — Bug caught by `loss.py`'s own self-test, not by inspection: `config/optim.yaml` originally wrote `unstable_penalty: 1.0e6`. PyYAML's `safe_load` in this environment parses that as the **string** `"1.0e6"`, not a float (a known PyYAML float-regex quirk — bare/loosely-formatted exponent notation doesn't always match its implicit float resolver). `compute_loss()`'s internal `float()` cast masked this from crashing, but the config value itself was silently wrong. Fixed by writing `1000000.0` instead; checked the rest of `joints.yaml`/`optim.yaml` for the same pattern (none found). - **2026-07-08** — Per user decision, replaced the plan's live optimizer-drives-simulator loop with an offline **collect-then-select** design: `collect_rollouts.py` samples a batch of {Kp, Kd, Fc} via Latin Hypercube (config/optim.yaml's `search` section) and simulates each one, saving results to disk immediately; `optimize.py` reads whatever's been collected (from one run or several resumed ones) and picks the best. Chosen directly because of the unresolved Isaac Sim stall — a batch-of-independent-rollouts design tolerates an individual rollout stalling or the whole process being killed and restarted, in a way a tight adaptive feedback loop would not. Trade-off: no longer a "smart" adaptive search (CMA-ES etc. would converge faster per-sample), but Latin Hypercube gives reasonable coverage for the sample budget, and nothing prevents running `collect_rollouts.py` again with narrower bounds around the first batch's best region as a manual second round.

Verified `optimize.py` end-to-end (best-selection, unstable-filtering, plot, YAML output) against synthetic fake candidate data with a known planted optimum — found a near-optimal candidate and correctly excluded 2 planted "unstable" entries. - **2026-07-09** — `collect_rollouts.py` rewritten to (a) fit each candidate against **every available training excitation type** (chirp/step/ramp/random) combined, not just one — a single motion type under-constrains the fit (chirp barely touches near-zero velocity, so it weakly constrains `Fc`; ramp is the opposite), so the combined (mean) loss across types is what's actually ranked, with per-type sub-losses kept for diagnosing which motion a bad fit fails on; and (b) loop over all 13 joints within ONE persistent `SimRolloutEngine`/Isaac Sim boot by default (`--joint_idx` still available to do just one), instead of requiring 13 separate process launches each paying the ~1-minute asset-load cost independently. - **2026-07-08** — `step`-type excitation trajectories use a **true instantaneous setpoint jump** (no software slew-rate limit), per explicit user choice, over slew-limiting to 1x/2x the rated joint velocity. Consequence: the automated position/velocity safety check in `make_trajectories.py`'s workflow must NOT apply the velocity-limit check to `step`-type trajectories — a step's finite-difference "velocity" over one `1/60s` sample is always huge (15-50 rad/s) by construction, regardless of step size, and that is expected/intended, not a bug. The check still applies the *position*-limit check to steps (step targets must stay within `joint_limits_rad`), and still applies both position AND velocity checks to `chirp`/`random`/`ramp`, which are meant to be continuously trackable references. Actual on-hardware safety for steps rests on the hand's own controller/firmware bounding real motion — not verified here, since this machine has no ROS/hardware connection to test against.

- **2026-07-09** — **The `Fc` (Coulomb friction) sweep was silently a no-op; set static == dynamic == fc.** `SimRolloutEngine.set_gains` called `write_joint_friction_coefficient_to_sim(joint_friction_coeff=0.0, joint_dynamic_friction_coeff=fc, ...)`. The 2 poisoned `rh_FFJ4` candidate `.npz` files from the pre-fix run were deleted (they would otherwise be reused via `collect_rollouts.py`'s skip-if-exists, keeping the inert `fc`) and collection was restarted from scratch.
