# Shadow Hand Lite PD-Gain Identification — Project Explainer

This document is the "explain it to a colleague" version of this project: what
problem it solves, why it's built the way it is, and how all the pieces fit
together. `README.md` is the quickstart/command reference; `DECISIONS.md` is
the dated, one-line-per-entry log of every non-obvious choice. This file is
the narrative that connects them.

---

## 1. The problem

We trained an RL policy for the Shadow Dexterous Hand Lite in Isaac Sim. To
run that policy on the *real* hand, the simulated hand's dynamics need to
behave enough like the real hand's dynamics that the policy doesn't fall
apart the moment it leaves simulation. Concretely, each joint in the sim is
driven by a PD controller with a stiffness (`Kp`) and damping (`Kd`) gain,
plus friction terms — and the values currently in the sim config are
placeholders (`Kp=1.0`, `Kd=0.1` uniformly), not measured from the real hand.

**Why we can't just calibrate torque directly:** the real hand's "torque"
readout is raw, uncalibrated strain-gauge differences — not real N·m. So the
obvious approach (measure real torque, fit a torque model) is unavailable.

**The approach instead: match motion, not torque.** If we command the same
joint-position trajectory to both the real hand and the simulated hand, and
tune the simulated hand's `{Kp, Kd, Fc}` (Fc = Coulomb/dry friction) until the
simulated trajectory matches the real one, we've implicitly identified the
gains that make the sim *behave* like the real hand — without ever needing a
torque measurement. This is standard system identification via "sim-in-the-
loop" optimization (the plan called it "Method 2").

---

## 2. Why per-joint, and why these three parameters

**One joint at a time.** Each of the Shadow Hand Lite's 13 independently
commandable joints is excited on its own, holding all others at a resting
pose. This keeps the fitting problem well-conditioned (13 small 3-parameter
fits instead of one 39-parameter joint fit) and easy to debug (you can look at
one joint's trajectory overlay and immediately tell if the fit is good).

**Three parameters, not four.** The plan initially asked for `{Kp, Kd,
Coulomb friction, viscous friction}` — four numbers per joint. We fit only
three: `Kp`, `Kd`, `Fc`. Viscous friction is fixed at 0 and folded into `Kd`,
because on a position-commanded joint, viscous friction and PD damping
produce the *exact same effect* — both are a torque proportional to
`-coefficient × velocity`. Only their **sum** is observable from motion data;
fitting them as two independent free parameters would let the optimizer trade
one for the other arbitrarily, which isn't a real fit, just an underdetermined
one dressed up as two numbers. Coulomb friction (`sign(velocity) × Fc`) *is* a
distinguishable nonlinearity, so it stays as a real free parameter.

---

## 3. The data: what's X, what's Y

Every `.npz` file in this project (generated commands, collected logs,
simulated rollouts) shares a schema built around this distinction:

- **X — the commanded trajectory (`cmd`)**: the joint-position setpoint we
  choose and send to the position controller at each timestep. Generated by
  `make_trajectories.py`, identical for both the real hand and the simulator.
- **Y — the actual/measured trajectory**: what the joint actually did in
  response to X. `actual_pos`/`actual_vel` from a real hardware log is
  `Y_real`; `SimRolloutEngine.rollout()`'s return value is `Y_sim` for a given
  candidate's gains, given the same X.
- **What's actually being fit is neither X nor Y — it's the gains**
  `{Kp, Kd, Fc}`. They play the role model *parameters* play in ML:
  `loss.py` scores how close `Y_sim` is to `Y_real` for the same X, and the
  search in `collect_rollouts.py`/`optimize.py` looks for the gains that
  minimize that score.

## 4. The pipeline, step by step

### Step 0 — Environment
Confirmed which conda env (`real2sim`) actually has this repo's `roto`/
`multimodal_rl` installed (others on this machine point at sibling repos with
the same package names — an easy silent-wrong-code trap), and that real
hardware collection needs a separate ROS/docker environment this machine
doesn't have.

### Step 0.5 — Excitation trajectory design (`make_trajectories.py`)
For each of the 13 joints, generates four kinds of motion, because each
excites different dynamics:
- **chirp** — a frequency sweep (0.05→2.5 Hz). The main tool for identifying
  `Kd`/damping, since it moves the joint at many different speeds.
- **step** — sudden setpoint jumps. Reveals `Kp` and transient/overshoot
  behavior. Deliberately a *true instantaneous* jump (no software slew limit)
  per an explicit choice — matches textbook step-response identification.
- **random** — a sum of a few random-frequency sinusoids. Covers
  speed/position combinations the clean signals miss. One random trajectory
  per joint (different seed) is set aside as **held-out** — never touched
  during fitting, reserved for final validation.
- **ramp** — one slow, quasi-static sweep. Exposes Coulomb friction (which
  only shows up clearly at near-zero velocity).

Every amplitude is derived, not eyeballed: for a sinusoidal component of
amplitude `A` and frequency `f`, peak speed is `A·2πf`, so the amplitude is
solved backward from the joint's rated velocity limit. This is why, e.g., the
coupled `FFJ2` chirp automatically uses a smaller swing than its position
limit alone would allow — the velocity constraint is the binding one at high
frequency.

### Step 1 — Load & clean (`load_data.py`)
Reads collected logs, resamples onto an even 60 Hz grid, applies a zero-phase
low-pass filter (10 Hz cutoff — a placeholder pending real noise data) so
noise isn't mistaken for real dynamics, and splits every log into train vs.
held-out **by an explicit flag stored in the file** (`meta_held_out`), not by
directory location — so the split can't be silently broken by a file ending up
in the wrong folder after a hardware-machine-to-here copy.

### Step 2 — Sim rollout engine (`sim_rollout.py`)
`SimRolloutEngine` boots Isaac Sim and loads the robot **exactly once**, then
exposes `.set_gains(...)` and `.rollout(joint_idx, cmd, default_pose)` to be
called repeatedly — critical because loading the asset is slow (~1 minute)
and Isaac Sim hangs for a long time on headless shutdown, so re-launching per
candidate would be prohibitively slow. Gains are set at runtime via Isaac
Lab's `write_joint_stiffness_to_sim`/`write_joint_damping_to_sim`/
`write_joint_friction_coefficient_to_sim` — confirmed to exist and work by
directly inspecting the installed `Articulation` class, not assumed.

### Step 3 — Loss (`loss.py`)
Compares simulated vs. real position (and derived velocity) sample-by-sample.
Two things are specific to this project's actual data, not generic
boilerplate:
- Every recorded trajectory has a real startup transient (the hand settles to
  a resting pose, then the recording begins mid-jump to the excitation's first
  commanded value) — the first ~30 samples are down-weighted by default, not
  just "optionally" as a generic system-ID text might suggest.
- A candidate's gains can make the sim numerically unstable (e.g. `Kp` too
  high). That returns a large **finite** penalty, not `NaN` — `NaN` would
  break most optimizers' internal comparisons, silently corrupting a search
  rather than just making one candidate look bad.

### Step 4 — Search (`collect_rollouts.py` + `optimize.py`)
See §5 below — this is where the biggest architectural deviation from the
original plan happened.

### Step 5 — Validation (`validate.py`)
Rolls out the selected gains against the joint's **held-out** trajectory (the
one the search never saw), computes position/velocity RMSE, and
appends/updates that joint's section in `results/REPORT.md` in plain
language. A joint failing its tolerance isn't necessarily a bad fit — it might
mean that joint has real backlash/stiction that a pure PD+Coulomb model can't
capture, which is a signal to consider a residual correction for that specific
joint, not a reason to keep re-tuning its PD gains indefinitely.

### Step 6 — Handoff (`emit_config.py`)
Turns whichever joints have been identified into a ready-to-paste Isaac Lab
config snippet (`stiffness={...}`/`damping={...}` dicts matching
`shadow_hand_lite.py`'s existing actuator config format) plus a commented
runtime-call snippet for Coulomb friction (which isn't a spawn-time config
field in this Isaac Lab version, only a post-spawn runtime call).

## 5. Why there's no live optimizer (and what replaced it)

The original plan called for a live loop: an optimizer (CMA-ES/Optuna)
proposes gains, the simulator evaluates them, the loss feeds back, repeat.
While verifying `sim_rollout.py`, we hit a **reproducible, unexplained
multi-minute stall** inside Isaac Sim on this specific machine, appearing
partway through even very short (3-second) rollouts. This was investigated
directly, not just suspected — and every alternative explanation was ruled out
by an actual test, not by assumption:

| Hypothesis | Test performed | Result |
|---|---|---|
| `sim.step()` itself is slow | Isolated diagnostic outside project code | Fast (50–90 steps/s) |
| Gain-dependent | Compared default-gain vs. 3×-gain rollout | Stalled at the *identical* sample both times |
| Headless rendering overhead | Passed `render=False` explicitly | No change |
| Network/telemetry timeout | `curl`/`ping` | Instant — network is fine |
| GPU clock throttling | `nvidia-smi` | GPU at P0 (max performance) |

The one consistent pattern: every run given enough patience eventually
produces correct output. So this looks like a severe but *bounded* stall
somewhere in Kit/PhysX, not a deadlock and not a correctness bug in this
project's code — but it makes a tight, synchronous optimizer loop
impractical, since any single call could silently hang for minutes.

**What replaced it: an offline collect-then-select design.**
- `collect_rollouts.py` samples a batch of candidate `{Kp, Kd, Fc}` up front
  via **Latin Hypercube sampling** (even coverage of the parameter space at a
  small sample budget — important since each sample costs a full Isaac Sim
  rollout), simulates each one against the real recorded command trajectory,
  and **saves every result to disk immediately** after it's computed — not
  batched at the end. This means the script can be killed mid-run (because of
  a stall) and simply re-started: already-collected candidates are detected
  and skipped, so no completed work is ever lost.
- `optimize.py` then reads whatever's been collected — from one run or
  several resumed ones — and picks the best candidate entirely offline, no
  further simulation needed. It plots the sorted loss across the batch as the
  honest substitute for a "convergence curve" (there's no sequence to plot
  when the search isn't adaptive, just an unordered batch).

Trade-off acknowledged: this isn't as sample-efficient as a smart adaptive
search would be. But it's robust to a stall of unknown, unpredictable
duration, which a tight feedback loop is not.

## 6. The finger-collision fix

While running real-hardware collection, a finger was observed colliding with
an adjacent finger during single-joint excitation. This mattered for two
reasons: hardware safety, and data quality — contact-perturbed motion isn't
explained by a model that only accounts for one joint's own actuator, so it
would have silently corrupted the fit for that joint.

**Root cause:** every non-excited joint was held at 0 (straight/open) during
excitation. A neighboring finger sitting straight is exactly in the path of
the excited finger's own range of motion.

**Rejected approaches** (both by explicit user direction):
- Shrinking the excited joint's own trajectory amplitude — this would corrupt
  the very identification we're trying to do (we want the joint's *real*
  full-range dynamics, not an artificially restricted subset).
- A precision `ContactSensor`-based calibration tool to tune small clearance
  angles — unnecessary complexity once the fix is "move neighbors all the way
  out of the way" rather than "leave a small gap": full clearance is obvious
  by inspection, no fine-tuning needed.

**Fix implemented:** every non-excited *finger* is parked fully out of the
way (curled toward the palm) while one finger is being excited, instead of
held at zero. Concretely:
- `config/joints.yaml` gained a `parked_finger_pose` section: one curled pose
  per finger (FF/MF/RF/TH).
- `make_trajectories.py`'s `compute_default_pose()` resolves this into a
  13-length baseline vector per excited joint (everything on other fingers
  parked; the excited finger's own other joints stay at 0) and embeds it as
  `default_pose` directly in every generated command `.npz` — the same
  pattern already used for `meta_type`/`meta_held_out`. This means the pose
  data travels to `collect_traj_hw.py` (which runs in a separate ROS/docker
  environment with no access to this repo's config files) automatically,
  through the file it already loads.
- `collect_traj_hw.py`'s `hold_zero` became `hold_pose(pose, ...)` (kept a
  thin `hold_zero` wrapper for the true full-hand safe-park at the very
  start/end of a run — that part is unchanged); the per-sample baseline
  changed from an all-zero array to a copy of `default_pose`.
- `sim_rollout.py`'s `SimRolloutEngine.reset()`/`.rollout()` and
  `collect_traj_sim.py` both gained a `default_pose` parameter and matching
  coupling-resolution logic, since a parked pose can put a *coupled* driver
  joint (e.g. `FFJ2`) at a nonzero curl while a different finger is being
  excited — that still has to resolve through the same driver/mimic split
  used for the excited joint itself.

**A real bug this surfaced:** while verifying the coupling-resolution logic,
`sim_rollout.py`'s existing `rollout()` method turned out to already reference
a position limit for the three *mimic* joints (`FFJ1`/`MFJ1`/`RFJ1`) that
`config/joints.yaml` never actually defined (it only ever had entries for the
13 *policy* joints). This was a latent `KeyError` waiting to happen for any of
the three coupled driver joints — never caught earlier because the one live
Isaac Sim test that had run to completion happened to use a non-coupled joint.
Fixed by adding the mimic joints' real limits (read from the live Isaac Sim
asset's own joint table, not guessed) to `joints.yaml`.

## 7. Known limitations, honestly stated

- **The Isaac Sim stall is unresolved**, only worked around. If it turns out
  to be fixable (e.g. a specific PhysX/Kit setting), the collect-then-select
  design could later be upgraded back to a live adaptive optimizer for better
  sample efficiency — nothing here prevents that migration.
- **Parked-pose curl magnitudes (~1.4 rad) are a firm parking choice, not a
  measured clearance angle.** A one-time visual sim check (running
  `collect_traj_sim.py` without `--headless` and eyeballing that parked
  fingers clear the excited one) is the recommended sanity check before
  trusting this on hardware, replacing the more precise (but unnecessary)
  contact-sensor calibration approach that was considered and dropped.
- **The 10 Hz filter cutoff in `load_data.py` is a placeholder** pending real
  encoder noise data — revisit once real logs exist.
- **Hardware timing jitter isn't recorded.** `collect_traj_hw.py`'s `t` array
  is a nominal step count (`step / 60`), not a measured wall-clock timestamp,
  so `load_data.py` can't correct for real ROS scheduling jitter, only for
  gross sample-count mismatches.
- **No real hardware data has been collected yet** as of this writing — every
  verification in this project so far has used either synthetic fixture data
  (for the non-Isaac-Sim pieces) or sim-generated stand-in data (for the
  Isaac-Sim-dependent pieces). The real test is once actual hand logs exist.

## 8. Where everything lives

| File | Role |
|---|---|
| `config/joints.yaml` | Single source of truth: joint order, limits, coupling constants, parked-finger poses |
| `config/optim.yaml` | Loss weights, candidate-search bounds/sampling settings |
| `src/make_trajectories.py` | Generates + safety-checks excitation trajectories |
| `src/load_data.py` | Loads/filters/resamples/splits collected logs |
| `src/sim_rollout.py` | `SimRolloutEngine` — persistent Isaac Sim instance, gains → simulated trajectory |
| `src/loss.py` | Scores simulated vs. real trajectory match |
| `src/collect_rollouts.py` | Samples + simulates a batch of candidate gains, saves each result immediately |
| `src/optimize.py` | Picks the best candidate from whatever's been collected, offline |
| `src/validate.py` | Held-out evaluation, updates `results/REPORT.md` |
| `src/emit_config.py` | Identified gains → Isaac Lab config snippet |
| `DECISIONS.md` | Dated log of every non-obvious choice, with the *why* |
| `README.md` | Quickstart and exact commands to run |
